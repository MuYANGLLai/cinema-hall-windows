# 第三方组件清单（Windows 分发包）

> 用途：Q1 已定 **路径 A（接受 GPLv3、整仓开源、Windows 端对外分发）**。这份清单是那条路上
> 唯一还欠的合规材料 —— 让拿到安装包的人能**逐个查到**包里每个第三方组件的版本、许可证、
> 源码位置，以及我们对它做了什么。
>
> 本文件只写**有证据**的条目。没核过的写在 §6「已知缺口」里，不在这里冒充已核。
>
> 事实来源：`docs/Windows-W7-交接审核.md` §6（2026-11-05 从本地 POM / jar / 上游仓库逐个取）；
> `docs/Windows-W7-开源前核对.md` §A（`vlc/` 371 个 PE 与 2325 个源文件逐文件扫描）；
> 逐文件证据表在 `docs/evidence/`。

## 1. 结论（三句话）

1. **这个包整体是 GPLv3**，因为 `vlcj`（GPL-3.0）与随包的 VLC（GPL-2.0-or-later）把整份作品拉到了 GPL。
   → 所以我们对**自己的**源码（`desktop/**`、`desktopApp/**`、`core/**` 等）也按 GPLv3 提供，不打折。
2. **里面没有 AGPL / MPL / EPL / CDDL**，不存在「必须换掉才能分发」的强 copyleft 之外的意外。
3. **唯一需要专门处理的**是 `jwebrtc.dll` 里静态链入的 FFmpeg（LGPL-2.1-or-later）：详见 §4。

## 4. `jwebrtc.dll` 里的 FFmpeg：这一条怎么落地（Q3 = A 的答案）

**事实**：`webrtc-java` 把 FFmpeg 的音频处理**静态编进** `jwebrtc.dll`（不是动态调用外部 `ffmpeg.exe`）。
静态链接时 LGPL-2.1 §6 要求：让接收者能把该库换成**他自己改过的版本**再重新拼起来。

**为什么在路径 A 之下这一条几乎自动满足**：

- 我们**不修改** FFmpeg，也不修改 `webrtc-java`，只是原样分发它们的产物；
- 整份作品按 GPLv3 分发的后果是**我们的全部源码都已公开**，接收者本来就能自行重建；
- LGPL-2.1-or-later 允许按 LGPL-3.0/GPL-3.0 使用，与 GPLv3 主体兼容，不需要额外许可动作。

**仍然要做的两件事**（不做就是漏）：

1. 在 §3 的 `SOURCE.txt` 里写清这份 FFmpeg 的**上游版本与源码地址**（不写，接收者找不到对应源码）。
2. 说明**可重链接材料的获取方式**：`jwebrtc.dll` 的构建发生在 `webrtc-java` 上游，我们没有它的构建环境，
   因此无法直接提供该 DLL 的目标文件。接收者若要求 §6 意义上的可重链接材料，走仓库 issue 联系，
   由我们向上游索取后转交；或在其本机按上游脚本重建 DLL。

**残留风险（如实写在这里）**：严格按 LGPL-2.1 §6 的字面要求，「提供目标文件」是分发者的义务，
我们把这一步转成了「提供源码 + 说明如何重建 + 承诺代为索取」。这条路在实务上通行，
但如果将来要**商业分发**，这条需要法务复核，或改成「动态链接 FFmpeg 的 webrtc-java 构建」。

## 5. 怎么复核这份清单（可复现，不需要设备）

```bash
# 1) 依赖树里到底有哪些 group:artifact
./gradlew :desktopApp:dependencies --configuration runtimeClasspath

# 2) 某个 jar 的许可证（POM 里的 licenses 段）
./gradlew :desktopApp:dependencies >/dev/null   # 先确保依赖已落盘
# 然后在 ~/.gradle/caches/modules-2/files-2.1/<group>/<artifact>/<ver>/ 下看 *.pom

# 3) 是否混进 AGPL / MPL / EPL / CDDL（期望：无输出）
./gradlew :desktopApp:dependencies | grep -Ei 'agpl|mpl|epl|cddl'
```

`vlc/` 目录那 371 个 PE 的逐文件判据见 `docs/Windows-W7-开源前核对.md` §A2，
原始扫描表在 `docs/evidence/vlc-3.0.21-pe-license.tsv`（可直接用 Excel / `column -t` 打开）。
